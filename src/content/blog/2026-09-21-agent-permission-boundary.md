我越来越觉得，Agent 安全真正的边界，不在于模型“会不会突然变坏”，而在于我们到底给了它什么权限。模型越能自主行动，这件事越不能继续按聊天机器人来理解：回答错一句话和拿着凭据进入一个系统，根本不是同一种风险。

最近一个很刺眼的信号是，Reuters 报道称，Google 的 Gemini 在一次由外部机构进行的网络安全测试中，曾自主进入三家公司的系统。Google 表示，这些目标被模型理解为测试范围内的站点，相关公司后来被通知，测试流程也做了调整。这个事件当然不能简单等同于“AI 失控”，但它提醒了一件更现实的事：当 Agent 可以浏览网页、调用工具、读取凭据、执行命令时，安全问题已经从“模型说了什么”转向“模型能做什么”。

一个常见说法是，只要模型足够对齐、红队测试足够严格，Agent 就会变得安全。我对这个说法越来越怀疑。模型层面的安全当然重要，但它解决不了所有执行层的问题。

第一，权限边界比模型意图更可靠。

我们很难证明一个复杂模型在所有环境里都会作出“正确判断”，但我们可以明确规定：这个 Agent 能访问哪些域名、能调用哪些 API、能读哪些文件、能否写入生产系统、单次最多花多少钱。传统软件安全里，最有效的办法从来不是期待程序永远不犯错，而是最小权限、隔离、审计和可撤销授权。Agent 不应该例外。

如果一个客服 Agent 只需要查订单，它就不该同时拥有退款、修改账户和导出客户数据库的权限。即便模型的错误率很低，权限给得过大，也是在把一个小概率错误放大成高损失事件。

第二，Agent 的问题正在从“提示词注入”升级成“权限链污染”。

Google 的 Mandiant 在 2026 年的 AI Risk and Resilience 报告里提到，企业 AI 已经从辅助查询工具走向能执行 API 调用、修改配置和串联工作流的自主系统。与此同时，攻击面也从单纯的聊天输入扩展到外部数据源、工具、插件和供应链。

这意味着，以后一次恶意网页内容、一个被污染的文档，甚至一个配置错误的 MCP 工具，都可能改变 Agent 后续的行动路径。真正危险的不是某一条 prompt，而是 Agent 在读取这条信息之后，手上恰好还拿着足够大的权限。

第三，企业真正需要的可能不是“更聪明的 Agent”，而是一个 Agent 权限操作系统。

今天很多团队讨论 Agent 框架时，重点仍然是规划、记忆、工具调用和多 Agent 协作。我认为接下来会有一层基础设施越来越重要：每个 Agent 的身份是什么，它代表谁行动，拥有哪些临时权限，一次任务的授权什么时候失效，每一步操作能不能追溯，异常时能不能立即冻结。

这听起来很像传统 IAM、零信任和审计系统，但 Agent 会把问题变得更动态。过去给一个员工授权，权限通常以月甚至年计算；未来给 Agent 的授权可能只应该持续十分钟，只允许完成一个任务，而且权限应该随着任务步骤逐步释放，而不是一开始全部给齐。

这也是我觉得当前很多 Agent 产品容易忽略的地方。Demo 里，“帮我完成这件事”越顺滑越惊艳；真正上线之后，企业更关心的可能是“它为什么能做到这一步”。

## 我可能错在哪

一个反对意见是，随着模型能力和安全训练继续进步，很多权限控制可能会显得过于保守，反而拖慢 Agent 的价值。就像早期互联网安全措施很繁琐，后来大量风险被浏览器、操作系统和云平台吸收，Agent 的安全机制也可能逐渐被模型提供商内置。

这完全可能发生。

但我仍然不太相信“模型自己判断什么时候该停”会成为最终答案。因为企业风险不是一个统一问题。同一个动作，在测试环境里可能完全安全，在生产环境里可能造成巨大损失。模型无法单靠通用训练理解每家公司的业务边界，它必须依赖外部权限系统告诉它：这里能做，那里不能做。

另一个可能是，我高估了自主 Agent 的普及速度。如果大量应用长期停留在“提出建议、人工确认”的模式，那么执行安全没有这么急迫。但最近的产品方向已经很清楚：浏览器操作、代码执行、自动采购、客服处理、网络安全等场景都在不断减少人工步骤。一旦这个趋势继续，权限问题不会消失，只会越来越靠前。

我下一步真正想查的，不是哪一个 Agent benchmark 又提高了多少，而是几家已经大规模部署 Agent 的公司到底怎么设计权限：有多少操作默认禁止，有多少权限是任务级临时授权，出现异常后多久能撤销，以及每一次 Agent 行动是否都能还原完整审计链。把这些问题查清楚，我觉得比单纯讨论“AI 会不会失控”更接近工程上的真实答案。
