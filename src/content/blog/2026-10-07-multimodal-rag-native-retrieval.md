我觉得 EmbeddingGemma 2 最重要的地方，不是 Google 又发布了一个 7 亿参数的小模型，而是它让我重新想了一遍很多 RAG 系统的默认前提：**为什么我们总要先把图片、视频和声音翻译成文字，才能检索？**

Google 在 10 月 6 日发布 EmbeddingGemma 2。完整模型 7.4 亿参数，把文本、代码、图片、视频和音频映射到同一个 768 维向量空间；根据需要可以只加载 2.7 亿参数的文本/代码部分，或者组合视觉、音频编码器。Google 还提供 128、256、512、768 维不同向量长度，并把模型直接放到端侧设备上运行。

这看起来像一个普通 embedding 模型升级，但我认为它指向的是另一种数据架构。

## 常见做法其实很绕：所有内容先“文本化”

今天很多所谓多模态知识库，底层仍然是文本系统。

图片先做 OCR 或 caption，视频先抽帧再生成描述，音频先 ASR，PDF 先解析布局，最后全部变成文字，再进入 embedding 和向量数据库。

这条路线最大的优点是工程成熟：文本模型多、工具链成熟、调试容易。

但它也有一个先天问题：**转换过程本身会丢信息。**

一张图片里“红色阀门旁边有一条细裂纹”，caption 模型可能只写成“工业设备上的阀门”；一段视频里某个动作发生的时间顺序，转录文本未必能表达；环境声音里机器转速异常的模式，ASR 更是什么都看不到。

如果检索层本身就能直接理解这些模态，很多中间翻译步骤可能不再是必选项。

## 第一层变化：Embedding 可能变成真正的多模态数据层

EmbeddingGemma 2 的设计很直接：不同模态用不同 encoder，但最后进入同一个向量空间。

这意味着一个文本查询可以直接和图片、视频片段、音频做相似度比较，不需要先生成中间说明文字。Google 的端侧演示里，用户可以用自然语言搜索本地照片，也可以直接在本地视频里找到某个具体时刻，不要求先完整转录和生成 caption。

如果这个思路成立，多模态 Agent 的数据结构会简单很多：

原始媒体 → embedding → 检索 → 把真正相关的原始内容交给大模型。

而不是：

原始媒体 → OCR/ASR/caption → 文本 → embedding → 检索 → 再回头找原文件。

少一层转换，不只是省 API 调用，也意味着少一层不可见的信息损失。

## 第二层变化：个人知识库和企业敏感数据可能更适合留在本地

Google 给出的端侧数据很有意思：在 Pixel 11 Pro 上，文本部分活动内存大约 191MB，完整多模态约 567MB。官方同时把它做进本地照片搜索、视频时刻检索和 Mac 上的会议助手实验。

我认为端侧 embedding 比端侧大模型更容易先形成实际价值。

原因是检索模型做的事情更窄：把数据索引好、快速找出相关内容。它不需要每次都生成长答案，也不需要几十亿、几百亿参数才能工作。

对个人助手来说，这尤其重要。真正敏感的信息往往不是用户主动上传的一份文档，而是整台电脑里的照片、会议音频、代码、聊天记录和本地文件。

如果索引过程完全在设备上完成，Agent 可以先在本地找到“哪些内容相关”，再决定是否把少量候选送给云端模型。隐私边界就会和今天“先把整个文件上传再问问题”很不一样。

## 第三层变化：Embedding 甚至可能承担一部分 Agent 路由

Google 这次还把模型描述成一个低延迟 decision engine：不做微调，直接把输入和一组标签或描述进行匹配，用向量相似度完成意图路由。

我觉得这件事有实际意义。

今天很多 Agent 每一步都调用大模型判断：

这是邮件任务还是日程任务？  
应该调用哪个工具？  
当前画面属于哪个设备状态？

有些判断其实不需要生成式模型。一个本地 embedding 模型如果几十毫秒就能完成粗分类，完全可以先做第一层路由，只把困难样本升级给大模型。

这会让 Agent Runtime 更像一个分层系统，而不是所有决策都交给最贵的模型。

## 风险在哪

多模态向量空间并不会自动解决所有检索问题。

Embedding 擅长“语义上像不像”，但企业检索经常要求精确事实：具体金额、零件编号、时间点、坐标、OCR 字段、数据库关系。这些内容仍然需要结构化解析。

视频同样如此。模型的上下文和采样策略有限，Google 默认的视频处理也需要抽取帧。对于高速工业视觉、细微缺陷或者复杂运动，一个通用多模态 embedding 未必能保留最重要的信息。

还有存储问题。统一向量空间虽然方便，但如果把数百万图片、视频切片和音频块全部索引，本地向量库仍然会迅速变大。Google 用 Matryoshka Representation Learning 把向量压到 128 或 256 维，本质上也是在承认：检索精度、存储和速度之间永远要做交换。

## 我可能错在哪

如果实际企业数据上，“先做高质量 OCR/ASR/caption，再用成熟文本 embedding”的召回率长期明显高于原生多模态 embedding，那么统一向量空间更多只是开发体验上的简化。

另一个可能是，端侧硬件虽然跑得动模型，但大规模首次索引照片和视频的耗电、发热、等待时间太高，用户最终仍然愿意把工作交给云端。

所以现在我不会断言文本化管线会消失。我的判断只是：**它第一次不再是多模态检索的默认唯一方案。**

## 下一步去查什么

我最想做一个很具体的对比：选一套真实混合资料——PDF、代码、设备照片、会议音频和视频——分别跑“原始模态直接 embedding”和“先 OCR/ASR/caption 再文本 embedding”，测端到端召回率、索引时间、存储、延迟和错误类型。

如果原生多模态路线在相近召回率下显著减少工程步骤，那 RAG 的架构可能真的该重画一次了。
