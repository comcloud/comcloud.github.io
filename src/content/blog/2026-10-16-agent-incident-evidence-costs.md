如果 Agent 可以替人完成真实操作，软件公司就不能再把错误只看作一次不满意的回答。我越来越觉得，企业部署 Agent 的一个隐藏成本，是出了事故以后能不能把“谁决定、谁授权、什么动作真的发生过”说清楚。

Axios 在 10 月 15 日报道，美国 FTC 已于 10 月 14 日向 OpenAI 与 Anthropic 发出民事调查要求，索取安全事故、保障措施、营销材料与隐私政策等记录。路透社随后转述该报道，并取得 OpenAI 表示愿意配合的回应。这里要强调：**这是媒体披露的调查取证，不是已经认定公司违法，也不是监管机构已经公开完整调查结论**。眼下重要的变化，是事故材料开始从企业内部工程问题变成外部审查可能要求提供的证据。

人们很容易把它简化成“监管开始要求 AI 更安全”。这句话没有错，却遗漏了软件工程里最难的一部分：对一个持续调用工具的 Agent，什么才算一次完整、可还原的事故？

## 记录工具调用，未必等于知道发生了什么

传统应用很熟悉审计日志：用户是谁、点了哪个按钮、接口返回什么。Agent 的执行过程却多了几层不稳定因素：同一个目标会被拆成不同计划，工具响应可能包含恶意内容，上一个任务的摘要会改变下一个决策，外部系统状态也可能在执行过程中变化。

假设 Agent 读取一份文件后又访问了一个网站。日志可以证明两个 API 曾经被调用，却未必解释它是否把原本应当留在内部的信息发送了出去。再比如一次网页提交失败后重试，最终到底产生了零个、一个还是两个订单？如果系统只存模型的文字解释，而没有外部服务的真实回执，这件事可能根本无法还原。

我倾向于把事故证据至少分成四层：任务和授权边界、执行时看到的输入、工具与外部系统的真实反馈、最终发生的状态变化。每层都要带上时间、模型和运行环境的版本。这听起来繁琐，但 Agent 一旦接触钱、个人数据或实体设备，少其中一层就可能留下关键空白。

## 第二个难点，是谁有资格解释证据

让执行 Agent 自己写事故报告，当然方便，却不能直接当成独立事实。模型可能不记得全部上下文，也可能把失败归因为错误的组件。即便没有任何恶意，它的“总结”仍然可能省略关键步骤。

所以我更关心一套与执行 Agent 分离的证据存储和复盘程序。原始工具响应、权限变化和外部回执应先被固定，再由独立检查程序重建过程。如果监测器只看到摘要，它就可能继承摘要里的遗漏。对复杂任务，最终还需要人能直接追到原始事件，而不是只能阅读机器生成的解释。

这会让一些团队重新认识沙箱的价值。沙箱当然要隔离不该触碰的目标；但同样重要的是，它要能证明在测试阶段有没有越过边界。没有可验证的隔离记录，“我们要求模型不要这样做”只是设计意图，不是事实证明。

## 第三层影响，是商业承诺需要有证据支撑

调查报道里，材料需求还涉及营销和隐私政策。这一点值得产品团队仔细理解：你在销售页面上说“Agent 只在授权范围内操作”，将来可能需要回答授权是怎样生成、检查和撤销的；说“不会泄露客户数据”，就要解释外部工具是否可能接收到敏感内容。

我的推断是，真正面向企业的 Agent 产品会把证据能力逐渐做成可出售的功能：版本固定、运行轨迹回放、敏感操作审批、结果核对和事后调查支持。安全不是只增加一层拒答模型，而是逐步进入产品的合同与验收流程。

但这一切都有成本。保存所有原始数据会带来隐私风险和存储费用；保留过少又不足以复盘。不同业务应当根据风险确定留存范围，而不是不加区别地长期保存所有用户内容。

## 我可能错在哪

也许后续调查没有形成任何违法认定，市场也不会因此显著改变采购行为。也可能标准化的执行协议很快降低审计成本，让我今天描述的“证据难题”变成云平台默认能力。更大的不确定性在于：多 Agent 行为跨越不同公司的系统后，没有任何单一参与方能掌握所有事实。

下一步我想查的不是谁收到了调查要求，而是公开的 Agent 事故报告究竟包含哪些可复核证据：有没有明确的外部影响、独立于模型叙述的工具回执、当时的权限状态和修复后回归测试。然后再找三家企业 Agent 产品，比较它们能否导出一份足以被第三方复盘的事故材料。这个答案可能比“模型安全分数提高了多少”更影响企业是否敢真正授权。
