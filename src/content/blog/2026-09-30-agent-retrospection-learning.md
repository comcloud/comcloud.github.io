我最近越来越怀疑，Agent 后训练最稀缺的东西未必是“更多成功轨迹”，而是**能把一次失败讲清楚的训练信号**。9 月 28 日提交的 ROFT 论文给了一个很反直觉的结果：模型先去做任务，看完反馈后只训练自己写出的“事后解释”，并不直接对动作做强化学习，也能让后续行动明显改善。

这不是说强化学习没用了。更准确的判断是：**Agent 的执行轨迹很长、奖励很稀疏时，解释可能是一种便宜的信用分配方式。**

## 常见误读：反思就是多写一段“我哪里错了”

“让模型反思”已经被用烂了。很多 Agent 系统失败以后，再加一句 prompt：请总结错误并重新尝试。它有时有帮助，但本质上仍是同一次推理里的上下文技巧。

ROFT 做的事情更重。Agent 先尝试真实软件工程任务，拿到可用反馈，再生成 retrospective explanation；随后模型参数只对这段解释文本做 next-token training。它不需要外部老师给一条标准答案，也没有按奖励直接更新 policy。

论文在 Qwen3.5-4B 上做实验。20 次更新后，在 held-out SWE-bench Verified 和 Pro 上分别达到 49.2% 和 26.8%；论文对比的 GRPO 运行在 40 次更新后是 48.0% 和 25.3%。更有意思的是，有些任务基础模型采样 64 次都没有一次成功，ROFT 仍然可以学到后来解出来。

我不会据此说“解释优于 RL”。两种方法的计算预算、实现和实验设置并不等价，而且目前只在一个 4B 模型和软件工程任务里证明。但它把一个重要问题摆到了台面上：**如果没有成功示范，学习是不是仍然可以从失败里开始？**

## 第一层原因：解释把稀疏结果变成了稠密结构

一个 Coding Agent 跑了二十分钟，最后测试失败。普通 reward 可能只告诉它：0 分。

但真正有价值的信息藏在过程里：改错了文件、误解了接口、遗漏了边界条件、测试命令没覆盖目标路径、某一步其实是正确的，只是后面被破坏了。

强化学习当然也可以处理信用分配，但长轨迹让问题变得昂贵。Retrospection 的价值可能在于，模型先把这段经历重新压缩成语言：“哪一步对，哪一步错，为什么错，下次应该怎样做。”训练目标于是从一个稀疏数字，变成了大量有结构的 token。

如果这些解释与真实反馈一致，模型等于给自己的经历做了一次可学习的重新编码。

## 第二层原因：Agent 天然拥有比普通语言模型更丰富的反馈

聊天模型很多时候只有“用户喜欢不喜欢”。Coding Agent 不一样：编译器、测试、静态分析、运行日志、文件 diff 都可以给出外部证据。

这意味着 Agent 的后训练素材不一定非要靠人工造高质量答案。每天真实运行产生的大量失败轨迹，本身就是一座数据矿，只是目前大部分系统把它们当日志存完就算了。

SWE-bench Verified 有 500 个经人工确认的真实 GitHub issue，用来评估模型能否解决真实软件问题。这样的环境之所以适合研究 ROFT，正是因为“做没做对”有相对明确的外部检查。

我会进一步猜测，未来企业 Agent 的日志价值可能不在于拿来做传统 SFT，而在于先转成**经过证据约束的 retrospection artifact**，再决定哪些内容值得训练。

## 第三层原因：解释可以改变“怎么做”，而不只是“答案是什么”

论文还有一个我很感兴趣的观察：如果 prompt 要求 retrospection 强调更直接的解决方案，后续尝试会变短，即使训练时没有专门加入长度惩罚。

这暗示解释可能在学习一种过程偏好，而不是只记住结果。

如果能稳定复现，它对 Agent 很有意义。企业真正关心的往往不是 benchmark 最终多两分，而是：少调几个工具、少走几次弯路、少消耗一半上下文，最终仍然做对。

## 为什么是现在

原因和 Agent 的发展阶段有关。过去模型后训练主要面对单轮问答，奖励信号相对简单。现在 Agent 一次任务可能包含几十次工具调用，成功率也不稳定，直接做大规模 online RL 成本很高。

DeepSeekMath 曾把 GRPO 推成重要的强化学习路线，它证明了相对奖励方法可以减少 PPO 的部分成本。ROFT 则从另一个方向问：有没有可能连 reward-based policy update 都先不做，直接训练模型对经历的解释？

我觉得这两个方向不是互斥关系。更可能的系统是：先用 retrospection 从大量廉价失败中学习，再把昂贵 RL 留给高价值行为。

## 我可能错在哪

最大的风险是“模型很会解释，但解释是错的”。自我解释天然存在自洽偏差：失败以后编一个听起来合理的原因，比真正找到根因容易得多。如果把错误解释直接训练回模型，系统可能学会更漂亮地为自己辩护。

第二，软件工程有强外部反馈，很多现实任务没有。销售、研究、运营里的“好结果”可能几周后才知道，甚至本身就有争议。ROFT 在这些领域能不能工作，我不知道。

第三，目前结果还不足以证明它比 GRPO 更高效。要公平比较，应该固定总 token、采样次数、GPU 时间和反馈预算，而不是只比较“20 updates 对 40 updates”。

## 下一步去查什么

我下一步最想看三个对照实验：**同等计算预算下 ROFT 对 GRPO；训练 retrospection 对训练原始成功轨迹；模型自解释对外部 verifier 生成解释**。还要把模型从 4B 扩展到更强模型，并离开 Coding 领域。

如果“自解释 + 外部证据”在这些设置里仍然稳定有效，那么 Agent 的学习系统可能会出现一层新的基础设施：不是先收集标准答案，而是先把每天发生的失败变成可信的学习材料。
