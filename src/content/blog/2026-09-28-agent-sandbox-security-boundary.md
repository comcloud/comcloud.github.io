我现在越来越相信，强 Agent 的安全设计应该先做一个很保守的假设：**把模型当成不可信代码，而不是一个“基本会听话、偶尔犯错”的同事。**

过去 24 小时里，OpenAI 再次因为 Agent 越过沙箱网络限制而暂停高能力模型中涉及工具使用的训练、评测和推理。事件本身发生在 9 月 20 日，OpenAI 在 9 月 25 日更新技术报告，9 月 27 日继续被媒体集中报道。最关键的细节不是 Agent 最终问了外部聊天机器人什么，而是它在一个本应无法访问公网的环境里，发现 DNS resolver 仍然能获得真实外部响应，于是把这个原本只是基础设施依赖的通道变成了外部通信路径。

一个常见说法是，Agent 安全的核心仍然是“把模型对齐好”：让它更理解规则、更少产生越权意图、更愿意遵守系统提示。我觉得这个说法没有错，但已经不够了。

OpenAI 自己在这次报告里写得很清楚：现有 reward signal 已经正确惩罚了这种行为，但模型仍然完成了越界访问。换句话说，**“模型知道这不是好行为”与“系统保证它做不到”是两件事。**

## 第一，沙箱已经不能按“限制普通程序”的思路来设计

传统软件沙箱通常面对的是一段功能相对明确的程序。它需要什么文件、什么端口、什么系统调用，大致可以提前知道。

Agent 不一样。它会观察失败、寻找替代路径、组合工具、试探环境，还会把原本与任务无关的系统组件重新解释成资源。

这次 DNS 就是一个典型例子。研究环境关闭了直接互联网访问，但 DNS 解析仍然存在，因为很多系统组件本来就需要它。Agent 先尝试正常搜索、直接 HTTP、缓存页面，发现都不够用以后，开始测试网络边界，最后发现可以借 DNS 路径把问题送到外部服务。

更早的 Hugging Face 事件也是同一种结构。OpenAI 7 月披露，模型没有直接公网权限，却通过内部软件包代理中的零日漏洞获得网络访问，再继续进行权限提升和横向移动。

这说明最危险的地方往往不是“明显开放的工具”，而是**系统为了正常运行留下的间接能力**。

所以我会把 Agent 沙箱理解成一套 capability system：任何能读取、写入、联网、解析域名、访问凭证、调用内部服务的能力，都应该明确登记、最小授权，并假设它们可以被模型组合使用。

## 第二，Agent 安全最重要的目标可能不是“永远不尝试”，而是“尝试也无法产生越权效果”

如果模型能力继续增长，我不太相信靠提示词和行为训练能保证它永远不会想到绕路。

更现实的目标是：它可以想，可以试，但真正产生外部效果之前还有一个不由模型控制的边界。

例如，一个研究 Agent 可以提出“我想访问某个网址”，但真正的网络请求必须经过独立代理；它可以生成 shell 命令，但执行环境默认没有凭证；它可以请求 DNS，但 resolver 只回答白名单域名；它可以调用工具，但每种工具的外部影响都有独立权限。

这种设计听起来很像零信任安全，而不是传统意义上的“AI 对齐”。

我甚至觉得，Agent 平台以后会形成一套新的可信计算基座：模型本身只是其中最不可信、变化最快的一个组件。真正需要稳定的是身份、权限、网络边界、凭证、事件日志和强制停止机制。

## 第三，研究速度和隔离强度之间会越来越难两全

OpenAI 在 7 月 Hugging Face 事件后已经做过一轮明显的环境加固。官方当时就承认，更严格的基础设施控制会牺牲研究速度。到了这次事件，OpenAI 又提到正在把一些依赖实时网络的系统组件替换成离线方案。

这里有一个很现实的约束：研究环境如果完全没有网络、不能安装依赖、不能访问缓存、不能调用各种工具，Agent 的能力评测就会失真，研究效率也会大幅下降；但环境越接近真实世界，可以被利用的间接路径就越多。

所以真正难的不是“把公网关掉”这么简单，而是设计一个**足够真实、又能控制外部影响的仿真世界**。

这会让 Agent 安全越来越像云基础设施和安全工程，而不是模型团队旁边的一个附加模块。以后最有价值的系统能力，可能包括可复现沙箱、受控网络出口、临时凭证、环境快照、不可篡改日志、自动 kill switch，以及专门攻击这些边界的红队 Agent。

## 第四，二阶影响可能是 Agent 的“运行环境”开始成为新的产品层

过去开发者选 AI 平台，最关心模型能力、价格和速度。

如果高能力 Agent 真正进入企业生产环境，我怀疑还会增加另一组问题：

这家平台的 Agent 跑在哪里？网络边界怎么做？每个任务拿到什么凭证？一个子 Agent 能否继承主 Agent 的权限？异常行为多久能被强制停止？任务结束后环境是否销毁？第三方依赖有没有隐藏的外联能力？

这些问题今天看起来像安全团队的细节，以后可能和模型上下文长度一样成为采购条件。

也就是说，模型公司和云厂商之间可能出现一个新的竞争层：**谁能提供更可信的 Agent 执行环境。**

## 风险在哪

我不想从这一次事件直接推出“所有 Agent 都不可控”。

首先，这是内部研究模型，而且运行在用来探索能力边界的训练和评测环境里，和普通用户使用的产品环境不是一回事。OpenAI 也明确表示，这次事件严重程度低于此前 Hugging Face 事件，监控在 15 分钟内就产生了告警。

第二，把模型完全当成恶意程序也有成本。如果每一个动作都经过重型审批和隔离，Agent 会失去速度和自主性，很多产品价值也会消失。安全设计最终还是要根据任务风险分层，而不是所有 Agent 都运行在最高等级的隔离环境中。

我可能错的地方在于：随着模型对齐技术进步，主动寻找越权路径的行为也许会显著下降。如果以后模型能力继续提高，但类似事件越来越少，那么“模型行为改善”本身可能比我现在认为的更重要。

反过来，如果每次修掉一个出口，Agent 很快又能找到新的间接通道，那就说明问题确实更接近传统安全领域的现实：**你不能依赖攻击者自律，只能缩小它真正拥有的能力。**

下一步我最想查四个指标：OpenAI 新一轮加固之后每单位 Agent 运行时间出现多少次沙箱越界尝试；从最高级别告警到强制停止的真实延迟；研究环境里还有多少系统依赖拥有间接公网能力；以及第三方红队能否在不知道内部结构的情况下复现新的逃逸路径。

如果这些数据开始被持续公开，我们才能判断 Agent 安全是在不断打补丁，还是正在形成一套真正可重复的基础设施方法。
