我现在越来越相信，Agent 最先真正改变专业工作的地方，未必是替专家做最聪明的判断，而是接管那些早就被证明有效、却因为太耗注意力而长期做不好的循环。GitHub Security Lab 9 月 24 日公开的 Fuzzing Taskflow，就是一个很典型的信号。

它表面上很像“AI 自动找漏洞”：给它一个 C/C++ 代码库，系统会分析适合测试的入口、生成测试 harness、运行成熟 fuzzing 工具、读取 coverage、决定下一轮该改什么，再对异常结果做归类和报告。

最容易出现的说法是：安全研究员要被 Agent 替代了。我觉得这个判断太快。

真正值得看的地方，是 GitHub 自己对问题的定义：fuzzing 技术已经很成熟，长期效果却经常受限于人类有没有持续维护 harness、观察 coverage、处理异常结果。也就是说，瓶颈很多时候不在“有没有算法”，而在“有没有人一直盯着”。

Agent 恰好适合这种工作。

## 安全自动化真正稀缺的，可能一直是注意力

Google 的 OSS-Fuzz 已经运行多年，覆盖大量开源项目。它自己的研究资料曾指出，很多项目的运行时 coverage 仍然不高，主要原因之一并不是 fuzz engine 本身不够强，而是现有 fuzz target 没有覆盖到足够多的代码路径。

这很符合软件工程的现实。

工具可以全天运行，但工具不会自己问：“这一块为什么一直没有覆盖？”一个人看完报告之后，会补一个 target、调整输入、换一个角度，再跑一轮。真正耗成本的是这个反复观察和调整的过程。

GitHub 的 Fuzzing Taskflow 把这件事做成了 Agent 工作流：模型负责决定下一步追什么、哪些 coverage gap 值得继续投入，底层执行仍交给传统安全工具。系统还会在收益变小之后停止继续扩大计算，而不是无限跑下去。

我觉得这里出现了一个很有价值的 Agent 模式：

**成熟工具负责确定性执行，Agent 负责持续选择下一步。**

这比“让大模型自己做所有事情”靠谱得多，也更容易进入企业软件体系。

## 为什么是现在：Agent 开始能维护长时间状态

早几年，LLM 也可以生成 fuzz harness。Google OSS-Fuzz 的研究已经做过类似实验：让模型为既有项目补新的 fuzz target，其中一部分项目确实提高了 coverage。

但一次生成和长期运行不是同一个产品。

真正持续的安全工作需要记住很多上下文：这个 target 上一轮为什么失败、哪个路径已经试过、哪些异常其实是重复问题、这次修改后 coverage 是否真的增加。过去聊天式模型每次都像重新开始，很难维护这种长期状态。

现在 Agent Runtime 开始拥有持久任务状态、工具调用、文件操作、结构化工作流和可观察日志，才让这类工作从“生成一个脚本”变成“维护一场长期 campaign”。

所以我认为 Agent 的能力提升不只发生在模型里，也发生在模型外面。

模型可能只提高了十几个百分点，但如果 Runtime 能让它连续工作几十轮、不重复踩坑、每一步都有结果反馈，最终系统能力会产生很大的差异。

## 第二个变化：安全工程师的价值会往“定义边界”移动

如果 Agent 可以自动完成大量重复分析，人还剩什么？

GitHub 的实现反而给了一个很清楚的答案。它没有声称 Agent 的漏洞判断可以直接进入生产结论。对异常结果的分类、原因分析和修复建议仍然可能出错，最终结果需要人工复核。

人的工作不是消失，而是往上移动。

过去工程师可能花很多时间处理：
- 测试入口是否能正常构建；
- 哪一部分代码始终没覆盖；
- 一个异常是不是重复；
- 是否值得继续跑更多计算。

以后更稀缺的问题会变成：
- 哪些代码资产应该优先测试；
- 哪类异常必须升级成人工处理；
- 什么证据才能证明一个问题真的影响公开接口；
- 哪些 Agent 结论可以自动接受；
- 一场测试什么时候应该停止。

这是一类很典型的职业迁移：从操作工具，转向设计规则和验证标准。

## 第三个变化：很多“专项安全项目”可能变成后台常驻任务

今天很多安全工作仍然以项目方式存在。做一次审计、跑一次专项测试、版本发布前集中检查。一个原因不是这些检查没有价值，而是持续做太贵。

如果 Agent 能把重复注意力成本降下来，一些原来不值得持续投入的代码会重新进入安全预算。

一个小型开源项目，也许没有专门安全工程师，但可以长期跑自动测试；大公司里大量边缘仓库，也可以先由 Agent 做背景检查，只把高价值问题交给专家。

这会产生一个很有意思的二阶影响：自动化未必让安全市场变小，反而可能扩大被检查的软件总量。

当单位代码的检查成本下降，过去没人管的“长尾代码”会开始进入检测范围。安全公司的商业模式也可能从一次性交付，慢慢变成持续服务。

## 第四个变化：做安全的 Agent，本身必须比普通 Agent 更受约束

这里有一个很现实的矛盾。

安全 Agent 需要读取陌生代码、运行构建流程、调用大量工具。它的权限天然比普通聊天助手大。如果运行环境控制不好，它自己就会成为新的风险来源。

GitHub 的开源说明明确提醒，这套 Fuzzing Taskflow 当前应放在可丢弃、受隔离的执行环境里，因为自动化系统会运行目标项目的构建流程和分析工具。这个提醒非常重要。

Agent 自动化程度越高，安全边界越不能依赖“模型应该知道什么不能做”。

真正需要的是工程约束：执行环境可以随时销毁，凭据最小化，网络访问受限，资源有上限，关键操作有完整日志。换句话说，安全 Agent 的价值不只是“更自主”，还要看它能不能在一个可控制的盒子里自主。

这和最近 Agent Runtime 的整体方向很一致：模型负责提出动作，执行权属于外部系统。

## 风险在哪

我目前最大的保留是，GitHub 这次公开的是一个很完整的工程系统，但还没有一套足够强的独立对照实验，证明它在固定时间和计算预算下，能稳定找到更多真实安全问题。

Coverage 提高是好事，却不等于一定找到更多高价值缺陷；异常数量增加，也可能只是增加人工 review 的工作量。

如果最后人仍然需要把 Agent 的每一条结论重新检查一遍，那么前面省下的时间，可能又在最后一步被吃掉。

我也可能高估了这种模式的通用性。Fuzzing 特别适合 Agent，是因为底层反馈很明确：coverage 可以量化，异常可以重现，测试结果可以反复验证。很多安全工作没有这么干净的反馈信号，自动化难度会高很多。

## 下一步去查什么

下一步我最想看到一个真正公平的对照：在同一批真实项目上，让 Agent 工作流、传统自动化和有经验的安全工程师使用相近预算，然后比较四个指标——新增有效 coverage、确认后的真实问题数量、每个问题需要多少人工复核时间、每个确认问题的总成本。

如果 Agent 只是把报告数量做大，这个方向不会形成长期价值；如果它能持续减少“没人愿意一直盯”的工作，同时不把更多低质量结果扔给人，那它很可能会成为软件安全里一层很基础的后台设施。
