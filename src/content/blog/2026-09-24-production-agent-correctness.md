我觉得，Coding Agent 接下来真正难跨过去的门槛，不是“能不能改对一个 GitHub Issue”，而是“这个补丁放进真实服务以后会不会继续正确”。SWE-Serve 新 benchmark 最刺眼的一组数字是：很多补丁在普通测试里已经过关，一到真实推理服务的端到端测试仍然会被淘汰。

SWE-Serve 的论文在 9 月 22 日提交，9 月 23 日进入 arXiv 新信息流。作者把 SGLang 最近的真实生产改动整理成 53 个任务，覆盖模型支持、运行时执行、公共 API、缓存系统、GPU kernel 等六类推理工程问题。每个任务在 CPU 或单张 H100 上运行，并使用隐藏功能测试、回归测试、端到端 serving 测试和部分性能门槛来验收。

11 个模型、31 种模型与 effort 配置中，最好配置的平均 pass@1 达到 75%。但更重要的是另外一个结果：在 19 个包含端到端 serving 测试的任务里，如果不算 E2E 测试，通过率约为 69.4%；真正把服务跑起来再测，最终通过率只有约 45.9%。也就是说，相当一部分“局部上已经正确”的补丁，放进真实调用路径就不再正确。

市场现在很容易把 SWE-bench 一类成绩理解成“AI 软件工程师已经快成熟了”。我觉得这个结论漏掉了软件工程最麻烦的一层：生产系统的正确性不是一个文件、一个函数或者一组 unit test 的属性。

第一，Coding Agent 越强，测试基础设施反而越重要。

人类工程师也会写错代码，但经验丰富的团队从来不把“代码看起来对”当作上线标准。真实推理服务还要考虑模型加载、API 兼容、缓存状态、并发、GPU 路径、性能回退和老功能是否被破坏。

Agent 可以更快地产生补丁，只会让验证需求更高，因为产出速度快了以后，人工 review 不可能同比扩张。真正限制 Agent 吞吐的，可能从“写代码需要多久”变成“我们能不能自动证明这次修改没有把服务弄坏”。

第二，未来 Coding Agent 的 benchmark 会越来越接近运行中的系统，而不是静态仓库。

SWE-Serve 的价值恰好在这里。它不是只比补丁文本和参考答案，也不是只跑几个 isolated tests，而是把模型服务器真的拉起来，用隐藏测试检查最终行为，并且对部分任务设置性能 gate。

这会改变一个重要的评测习惯。过去 Agent benchmark 常常问“issue 是否修复”；以后更合理的问题会是：用户请求是否成功、延迟有没有退化、显存有没有爆、旧模型还能不能服务、重启以后状态是不是正确。

对企业来说，这种评价比榜单上多几个百分点更接近采购决策。一个 Agent 如果补丁写得快，却需要资深工程师反复收拾线上问题，它的真实生产率很可能是负的。

第三，Inference Engineering 是一个很好的压力测试，因为它天然跨层。

推理服务的改动经常同时碰模型结构、GPU kernel、调度、缓存、API 和测试。一个 Agent 如果只擅长局部代码生成，很容易在某一层“做对”，却破坏另一层。

这也解释了为什么未来高价值 Coding Agent 不会只依赖更聪明的模型。它还需要能启动服务、读取指标、构造负载、比较性能、保留失败证据，并在验证失败后准确定位到是哪一层出了问题。模型能力只是其中一部分，真正的产品是模型加执行环境加 verifier。

第四，企业软件团队最值钱的数据可能逐渐变成“生产失败是怎么被发现的”。

GitHub Issue 和测试用例很容易被拿来训练，但真实生产里最有价值的信息往往来自事故：某个补丁为什么在高并发才出错，某次版本升级为什么导致尾延迟增加，哪种配置只在特定 GPU 上失败。

如果这些事件能够被整理成可重放环境和隐藏测试，它们会成为很强的 Agent 训练资产。企业以后部署 Coding Agent，可能会发现自己的 CI、回归集、性能基线和事故库，比选择哪一个通用模型更难复制。

## 风险在哪

SWE-Serve 只有 53 个任务，而且高度集中在 SGLang 和推理 serving，不能直接代表普通 Web 开发、移动应用、数据库或大型企业系统。75% 也只是 benchmark 里的最好配置，不等于 Agent 已经能独立维护生产推理平台。

第二，端到端测试也不等于生产真实世界。它仍然是可复现的受控环境，无法完整覆盖流量分布、网络故障、跨服务依赖和长期状态问题。

第三，我可能高估了“生产正确性”会成为模型厂商的竞争点。很多企业也可能继续采用保守工作流：Agent 只写代码，人类和现有 CI 决定能不能上线。那样的话，验证能力会留在企业 DevOps，而不是 Coding Agent 产品本身。

什么证据会推翻我的判断？如果未来 Agent 在真实公司的 merge 后故障率和人工返工率持续接近资深工程师，即便 benchmark 只做仓库级测试也没有明显差距，那么生产 E2E 评测的重要性可能被我高估了。

我下一步最想查的是：Agent 生成的补丁真正进入生产以后，多少会触发 rollback；E2E、性能和回归测试分别拦住多少错误；人工 review 时间有没有随着 Agent 使用下降；以及真实事故能不能稳定转化成下一轮可执行的 verifier。Coding Agent 真正成熟的标准，可能不是“能修多少 Issue”，而是它提交的代码能不能让值班工程师少半夜起床。
