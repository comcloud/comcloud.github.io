今天很多手机 Agent 的默认想象是：模型像人一样盯着屏幕，每走一步截一次图，再让 VLM 判断下一步点哪里。这个路线很直观，也最容易做 Demo。但 9 月 28 日提交的 PhoneCLI 让我觉得，真正能规模化的手机 Agent 也许会走向另一种结构：**把重复的界面导航提前“编译”，只有遇到新问题时才重新看屏幕。**

这听起来像在倒退——模型都已经会看图了，为什么还要做地图和确定性命令？我反而认为这可能是 Agent 工程成熟的信号。聪明不应该意味着每一步都重新思考。

## 常见误读：GUI Agent 不够好，是因为 VLM 还不够强

传统移动 GUI Agent 的执行循环大致是：截图、送进 VLM、理解当前页面、生成点击或滑动动作、再截图。

它的优势是通用，只要人能看懂，理论上模型也能操作。但代价同样明显：每一步都有视觉推理延迟，每一步消耗 token，每一步都有概率判断错误。一个原本只需连续点三次固定菜单的任务，也要重复调用大模型。

PhoneCLI 的思路是先离线探索 App，从外部观察不同 screen、interactive element 和 navigation edge，构建带语义标注的导航图。每个可达页面可以对应一条确定性的 replay command。在线任务里，Agent 先选命令、执行前验证状态，然后直接快速执行；路径失效或遇到开放式交互时，再退回普通 VLM Agent。

论文特别强调，它编译的是 App 的导航结构，而不是记住某一次任务，因此新任务只要复用同一段导航，也能受益。

## 第一层变化：Agent 可能开始拥有“热路径”和“冷路径”

软件系统里早就接受一件事：常走的路径应该被缓存、编译、优化，不需要每次从第一性原理重算。

Agent 今天却经常反过来。即使用户每天都执行“打开报销 App → 进入待审批 → 打开某条记录”这条路径，模型每天都重新识别三个页面。

如果 PhoneCLI 的思路扩展，我觉得 Agent Runtime 会自然分成两层：

**热路径**：稳定、高频、可验证的行为，转成确定性 skill 或 command。

**冷路径**：新页面、异常状态、开放式任务，才调用昂贵的大模型重新解释。

这不是把 Agent 变笨，而是把大模型留给真正需要判断的地方。

## 第二层变化：模型的价值可能从“每一步执行”转向“发现可复用结构”

PhoneCLI 目前主要是离线探索和编译导航，但这个思路继续往前走，会出现一个很有意思的方向：Agent 自己发现哪些轨迹反复出现，然后把它们提炼成可验证技能。

过去大家讨论 Agent Memory，多数想到“记住用户喜欢什么”。另一类 Memory 可能更有工程价值：**记住这个环境里已经学会的操作结构**。

例如企业内部系统有几十个页面，但员工真正每天使用的路径可能只有几十条。第一次由 VLM 探索，之后生成稳定 command；页面改变后验证失败，再触发重新探索。Agent 就从“每次现场 improvisation”变成“持续维护一个环境操作模型”。

## 第三层变化：这可能改变 App 和 Agent 的关系

如果 GUI Agent 大量采用这种路线，App 开发者会面临一个选择：继续让 Agent 猜像素，还是主动暴露更稳定的语义状态和可调用路径。

AndroidLab 在 2024 年建立了 138 个任务、9 个 App 的 Android Agent benchmark，当时开源模型在训练后依然只有相当有限的平均成功率。几年下来，模型已经强很多，但 GUI 操作依旧被延迟、页面变化和错误累积困扰。

我怀疑真正的终局不会是“VLM 把所有 App 像素看得越来越准”，而是 App 逐渐出现一层 agent-friendly interface：页面仍然给人用，同时提供稳定的 semantic route、action schema 和 state verifier。

这会让 GUI 从最后手段变成兼容层，而不是 Agent 的唯一接口。

## 为什么是现在

因为 VLM 终于强到足以完成探索，却也贵到让“每一步都调用”显得浪费。

在模型还看不懂界面的时代，编译没有意义；没有第一次正确探索，就生成不了可靠命令。现在模型足够强，第一次探索的产物反而可以被固化下来，形成后续更便宜的执行路径。

这和 Coding Agent 里的环境缓存、工具技能、context compaction 是同一类趋势：**把一次昂贵推理的结果沉淀成以后可以复用的软件结构。**

## 风险在哪

最大的问题是现实 App 没有 benchmark 那么稳定。A/B 测试、地区差异、动态列表、登录态、弹窗、广告、字体缩放都可能让预编译路径过期。

所以 PhoneCLI 真正关键的不是“command 很快”，而是执行前 verification 和失败后的 VLM fallback。没有这两层，编译路径只会把偶发错误变成高速错误。

第二，离线探索本身有成本。对于低频 App，建立完整导航图可能比直接用 VLM 更贵。只有高频路径和高复用场景才能摊薄成本。

第三，我不知道这种方式在银行、支付、医疗等强状态 App 里是否仍然可靠。很多页面表面一样，背后账户状态不同，仅靠视觉和导航图可能远远不够。

## 下一步去查什么

我下一步想看的不是 PhoneCLI 在单次 benchmark 上又省了多少 token，而是**一个真实 App 连续更新 30 天后的 command 命中率和失效率**。最好同时记录页面更新次数、验证失败率、VLM fallback 比例、平均任务成本和最终成功率。

如果一个月后，大部分高频导航仍能走编译路径，而新页面又能被及时发现和重建，那“Agent 编译器”才可能成为移动 Agent 的基础设施。否则它更像一项只适合静态 benchmark 的漂亮优化。
