我越来越觉得，今天 AI 安全争论里最容易被说空的一句话，是“我们愿意承担一定风险”。真正的问题从来不是风险存不存在，而是谁决定多少风险算可以接受，以及事故真的发生以后，成本落在谁身上。

10 月 4 日，Reuters 报道了 Sam Altman 对 Politico 的一段采访。他明确表示，AI 带来的收益足以让社会接受“一些坏事发生”，并强调普通人应该拥有使用这项技术的自主权。一天前，前 OpenAI 安全负责人 David Robinson 离职后公开提出相反担忧：随着系统能力提升，靠快速发布、出问题再修的“试错式部署”已经越来越难承受。OpenAI 对此回应称，公司会确保模型能力不超过其可以安全管理和保护的范围，并在需要时暂停训练或推迟发布。

把这两件事放在一起看，我觉得真正出现的变化不是“安全派和发展派吵得更凶”，而是 AI 已经从一个主要产生答案的软件，变成了会调用工具、持有凭证、操作网页、访问代码库甚至长期运行的执行系统。过去软件行业熟悉的试错方法，开始碰到它自己的边界。

## 软件时代的试错，默认失败可以回滚

互联网产品有一套非常成熟的方法：先上线，再看日志，再 A/B 测试，出了问题就回滚。这个模式之所以有效，有一个经常被忽略的前提——大部分错误是可逆的。

页面改坏了，可以回滚版本；推荐算法效果差，可以撤掉实验；一个按钮放错了位置，最多损失一段时间的转化率。

Agent 不一样。

如果一个 Agent 发错邮件、上传了不该上传的文件、使用泄露的 API Key、下错订单，或者访问了一个并不属于测试范围的外部系统，后果可能在发现错误之前就已经离开公司的控制范围。你可以回滚代码，但不能保证收件人“没看过那封邮件”，也不能让已经外泄的数据自动回来。

这意味着 Agent 时代的风险单位，不该只是“模型输出错误率”，而应该是**不可逆外部动作的概率 × 后果**。

## “用户有选择”并不能自动解决第三方承担成本的问题

Altman 强调技术应该广泛可用，这个逻辑有它非常现实的一面：如果能力只掌握在少数实验室手里，创新、竞争和普通用户的选择都会受限。

但这里还有另一层经常被忽略的问题：使用者获得收益，未必由使用者承担全部失败成本。

一个开发者让 Agent 自动研究网络漏洞，他得到效率提升；如果 Agent 越过测试边界，成本可能由一个毫不知情的网站承担。一个企业让 Agent 自动处理客户资料，它节省人工；如果权限设计不好，泄露风险落在客户身上。

所以“接受多少风险”其实不是一道单纯的技术题，也不是一句价值判断就能回答的问题。它至少需要拆成三个对象：**谁获得收益、谁有权做决定、谁承担损失。**

如果这三者不是同一个主体，试错成本就可能被转移出去。

## 真正有用的安全，可能越来越像工程约束，而不是模型承诺

我不太相信未来 Agent 安全主要靠把模型训练得“更有安全意识”。这当然重要，但它很难成为最后一道防线。

更现实的方向是把安全直接做进运行系统：

- Agent 默认只拿到最小权限，而不是先给完整权限再靠模型自律；
- 高风险动作在真正提交前经过确定性的权限和状态检查；
- 外部网络、文件系统、支付和账号操作拥有独立边界；
- 每一次真实动作都留下可追溯记录；
- 出现异常以后能够快速冻结凭证、终止任务并保存证据；
- 模型升级之后，过去出现过的问题自动进入回归测试。

OpenAI 在 2026 年 5 月发布的 Frontier Governance Framework，本身已经把风险评估、事故响应、外部专家参与等写进治理框架。这说明即便支持较快部署的一方，也并不是在主张“没有安全措施”。真正的争议更接近：**哪些风险可以通过运行时工程控制，哪些风险在能力继续提高以前必须先降低。**

## 二阶影响可能发生在企业采购，而不是公众争论里

企业真正买 Agent 时，很可能不会先讨论宏观的 AI 风险哲学。它们会问更具体的问题：

这套系统出了事能不能追责？谁能停掉它？权限能不能按任务缩小？凭证有没有隔离？一次误操作的最大损失是多少？日志能不能复盘？

如果这些问题逐渐进入保险、采购和合规合同，安全就会从“成本中心”变成商业参数。两个能力差不多的 Agent，一个能把最坏事故限制在几百美元和一份临时文件里，另一个可以触达核心生产系统，它们的企业价值不会一样。

我甚至怀疑，未来 Agent 产品最重要的一个指标可能不是 benchmark，而是**每一万个真实任务里，发生多少次需要人工接管的高风险异常，以及这些异常平均多久能被发现和停止。**

## 风险在哪

我可能高估了这些事故的频率和经济影响。

如果未来几年的真实数据证明，高权限 Agent 在大规模部署下依然极少产生严重外部事故，而且监控、沙箱和权限控制能够把绝大多数问题限制在很小范围，那么快速试错仍然可能是更有效的发展方式。

反过来，过度限制也可能产生真实成本。只有大公司能负担复杂安全体系时，严格要求反而可能强化头部公司的地位，让小团队很难参与。

还有一个最难的问题：极低概率、高后果事件本来就很难用短期数据估计。没有事故，不等于风险为零；出现一两次事故，也不等于整个技术路径不可用。

## 下一步去查什么

我下一步最想持续追踪的，不是哪位 CEO 又说了什么，而是四个可以量化的数据：公开部署的 Agent 每万次任务发生多少次高风险异常；异常从发生到检测需要多久；有多少外部动作能够真正撤销；企业在合同和保险里如何给 Agent 事故定价。

如果这些数据开始公开，我们才有机会把“AI 应该承担多少风险”从立场争论，变成一门可以比较的工程和经济问题。
